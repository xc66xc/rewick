# 运营观测部署与验收

业务 PostgreSQL 保持原有版本和数据。性能明细使用独立 PostgreSQL 15.19；趋势使用 Prometheus v3.15.0。两个容器各限 256 MB / 0.25 CPU，均无宿主机端口映射。管理页面通过已有管理员 API 查询，不能提交 SQL 或 PromQL。

## 部署顺序

1. 保留旧后端 JAR、管理静态资源与镜像标签。记录原 Compose 配置；独立监控卷不参与业务数据库回滚。
2. 将 `compose.operations.yaml`、`prometheus.operations.yml`、`scripts/prepare-operations.sh` 上传到原部署目录。运行 `bash prepare-operations.sh`：在服务器生成私有密码和抓取令牌，启动两个监控容器。现有 `.env` 不改写；业务供应商、SMTP、支付配置仍来自管理后台。
3. **手工**将 `backend/sql/operations/01_operations.sql` 执行到新监控库，不能在业务库执行。它安装固定监控表、日分区及保留维护函数；后台仅维护这些分区，不自动创建业务表或执行业务迁移。
4. `backend/sql/24_operations_statistics.sql` 是业务库可选统计索引，使用 `CREATE INDEX CONCURRENTLY`，单独执行，不能包在事务中。统计查询每分钟后台更新缓存，单条查询限时一秒。
5. 校验产物哈希后发布后端与管理端。默认采集关闭；先在「运营观测 → 采集设置」启用少量测试用户，核对独立泳道、业务响应和遥测积压，验证后再扩大范围。启用但灰度名单为空表示所有用户。
6. 可运行 `python3 verify-operations.py` 验证服务器协议。该脚本使用临时令牌和合成事件，不调用模型、支付或 ASR；结束后恢复关闭状态、撤销临时令牌并删除合成明细。

私有文件 `.operations-backend.env`、`.operations-database.env` 为 600；`config/` 为 700。Prometheus 仅绑定读取 `config/operations-metrics-token`，不要把这些文件提交 Git、打印到终端或打入镜像。

## 口径和故障边界

- 最近七天明细不主动采样；九十天聚合不保留用户、操作或模型名称。容量清理可以提前删除最旧分区，管理页显示实际可查询起点。
- PostgreSQL 清理预算为 2 GB，Prometheus 保留设置为 1 GB。它们是软预算，Prometheus 的 WAL/head、数据库 WAL、镜像与日志不属于保留文件大小的硬配额；需要同时监测宿主机剩余空间。容量不足可以停用采集或迁移监控服务。
- 桌面缓冲最多 200 条 / 2 MB，低流量每十秒上报；积累到 64 条时异步提前发送，单批最多 64 条 / 256 KB，失败仍按十秒节奏重试；后端队列最多 2,000 条 / 8 MB，包含正在异步写入的批次。失败最多重试两次，超过两分钟放弃。队列和存储故障不会等待业务完成，也不会跨账号补传。
- 会话保存和同步通过有界的最近回答关联表复用对应操作 ID；合并保存按实际执行次数记录，不补造每个回答的同步事件。
- 客户端与服务器分别使用单调时钟计时。未采集、旧桌面、自定义供应商没有平台阶段的情况显示缺失，不能从时间戳差推测网络延迟。
- 首正文排除空消息、心跳与空白内容；首次渲染指 React 提交。并行 RAG/Tavily 不相加。取消、超时和拒绝分类保留；实际返回的 token 才计入覆盖样本。
- 业务数据来自原数据库，不用于补造历史性能。活跃用户固定为北京时间当天开始面试的普通用户；扣除时长来自 `consume` 账本。付款成功率按订单创建批次计算，退款和付款金额分开显示。
- 监控服务不可用、丢弃计数和存储预算告警只在管理页提醒。立即停用采集后，已在队列中的数据可丢弃；不会自动重试业务请求或切换供应商。

## 验收命令

从仓库根目录运行：

```sh
node deploy/server/scripts/operations-benchmark.mjs
```

它运行真实桌面服务的并行检索与自定义模型流，使用本地 HTTP 模拟供应商，分别测试高负载开关对照、队列故障和正常十秒上报。高负载下的主动丢弃单独报告，不等于全量上报覆盖率。

真实 Electron / IPC / Java / 双数据库验收：

```sh
cd frontend
npm run test:operations
```

需要最新后端 JAR、本地规定版本的 PostgreSQL/pgvector 镜像。测试创建独立数据库与账号，使用复制后的不可变 JAR，并在结束时清理资源。不会连接生产供应商。

Java 负载对照可以与 Electron 测试夹具配合：为其设置 owner-only 临时文件 `OPERATIONS_SMOKE_READY_FILE`；收到 READY 后，从根目录用相同变量运行 `node deploy/server/scripts/operations-backend-benchmark.mjs`。脚本结束写入 `.done`，Electron 测试继续。结果写入忽略提交的 `frontend/test-results/`。

验收目标是关键路径新增 P95 ≤5 ms、吞吐下降 ≤2%。桌面服务、Java HTTP、Electron 行为及生产资源分别报告，不能把其中一项的结果当成全链路性能承诺。

## 回滚

先在采集设置停用，再将 backend 镜像/JAR 与 admin 静态资源恢复到同一备份版本。需要完全恢复原拓扑时，移开 `compose.override.yaml`，按原 Compose 重建 backend；停止独立监控容器，但不要删除监控卷。新增业务索引可以保留，不需要恢复整个业务数据库。原供应商配置、额度、认证主体与业务幂等协议均继续使用原逻辑。
